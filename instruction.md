I used to watch the token counter the way you watch a taxi meter in a city you don't know. A moderate full stack app, vibecoded end to end in Claude Code, would quietly run me thirty to eighty dollars in API credits, and I would tell myself it was the price of speed. It wasn't. Most of what I was paying premium rates for was generation, not reasoning, and generation does not deserve premium rates. So I split the job. qweb does the building. Claude Code does the thinking.

The qwen I use is the free chat at chat.qwen.com/a/chat. Not the API, not a paid tier, not a proxy through some wrapper that charges you for what qwen gives away. The chat is 100% free. No credit card, no subscription, no hidden caps. You get DeepThink reasoning, file uploads, web search, and the full context window, all at zero cost. There is no paid consumer product to upgrade to because free is the whole thing. The only tax is slower responses during peak traffic, which shows up as waiting, not as a bill.

qwen is somewhere between forty and a hundred times cheaper per token than Claude for the API anyway, but since I am using the free chat, the number that matters is zero. And it writes code that is genuinely good enough for CRUD, parsers, integrations, refactors, and test scaffolding. It has a context window large enough to swallow an entire mid sized project. It can also output four thousand lines of code in a single prompt. I have had it produce an entire a.py script with twenty file writes, ten patches, a test runner, and all the raw string content embedded, in one shot, and the script ran green on the first try. That is the part that changes the economics completely.

The workflow starts with a bundle. I keep a script in every project root that walks the tree, skips secrets and build artifacts and node modules, and writes one text file to Downloads with clear file delimiters. That file is what I paste to qwen. qwen can analyze bundles up to around three megabytes of code, which is a full mid sized project including every config file, every pattern, and every test. It reads the whole thing in one shot. No file by file back and forth, no re explaining context on every turn, no paying to upload the same codebase forty times. The skip list matters more than people think. If qwen sees a real API key in context it gets hesitant about writing auth code, and scan artifacts and git metadata add noise without adding signal.

Two toggles change everything about how qwen performs. DeepThink is the reasoning mode, and it makes qwen slow down and think through the plan before answering. Without it, qwen rushes, produces code that looks right until you run it, and misses its own logic errors. With it, qwen catches most of those errors before you do, and every prompt in this workflow assumes DeepThink is on. Search gives qwen live web access, so when it needs to check a library version or an API signature or a framework gotcha, it looks it up instead of guessing from stale training data. That alone prevents a large share of the bugs I used to hit. Together, DeepThink plus Search makes qwen roughly five times more useful for planning and code generation. Without them you are not really getting qwen. You are getting the fast but sloppy version.

The planning step is where most people fail. They open qwen and say build me a SaaS, and the model produces something half formed, and they iterate for ten messages, and by the end they have burned the equivalent of a Claude Code session and have a mess. The better move is to write the plan yourself first. What the app is, every module and what it owns, every file the project will contain, the order files should be created, any hard constraints. Then ask qwen to split that plan into phases organized by file touch, not by feature. The naive way to phase a project is by feature, auth then dashboard then payments, and the problem is that config.yaml gets touched in all three, and main.py gets touched in all three, and every phase qwen has to remember what it did before. By phase three it is rewriting over phase one, or dropping fields it added two phases ago. The better way groups work so each file is touched exactly once, ever. Phase one is contract and foundation. Phase two is content layer. Phase three is orchestrator. Phase four is new capabilities. Phase five is UI integration. Phase six is benchmarks and docs. Every file lives in exactly one phase, and that is the invariant I enforce hard. If I realize in phase three that I need to add something to config.yaml that I forgot in phase two, I do not go back. The edit goes into phase three, and config.yaml becomes part of phase three forever. It sounds restrictive, but it is exactly what keeps qwen from getting lost.

qwen's job is not to produce snippets I paste into an editor. It is to produce one Python file per phase that does all the file writes and edits automatically. I always call it a.py. It lives in the project root, gets overwritten each phase, and is on the skip list for bundling. The shape is always the same. A write helper, a patch helper, one raw string per file to create, and a main that runs the phase tests at the end. It is idempotent, safe to run twice, which matters because the next step happens constantly. You run python a.py. If it fails, you paste the traceback back to qwen and say fix a.py and output the whole file again. Two or three iterations. Cheaper than one Claude Code file edit. And I don't bother with backups anymore. Claude Code is the safety net. If a.py breaks something, the traceback is a paste away from a fix, and git covers the phases that already went green. Local backups just add noise to the bundle and confuse the skip list. If a phase feels risky enough to need a manual backup, that is a sign the phase is too big and should be split.

Here is the exact prompt I open with when starting a phase. I paste it in verbatim, no cleanup, no hedging.

Now I am using qwen to create a Python script that edits, adds, and changes files, and runs commands to implement the changes. I have an a.py file where I always paste the qwen response, and I will run that response as a.py. I want you to create the paste for phase one. No comments in the code. Do not create any backups, I have Claude Code that can assist me to debug your output. Do the phase one first.

That last line matters more than it looks. Claude Code is not just my reviewer, it is my debugging partner. Telling qwen that explicitly changes how it writes code. It stops being defensive. It stops adding try-except blocks for every possible failure mode. It stops trying to handle every edge case in code, because it knows a human plus a second AI is downstream to catch what breaks. The result is cleaner, faster, more direct scripts.

The other prompt I paste is the one that sets the tone for planning and analysis.

You are a senior software engineer. Act like an expert code reviewer. Use web search to verify your verdicts and strengthen your knowledge, and deep think through every decision. Do your best analyzing the project. Go on, do your best.

I open every planning session with that. It primes qwen to behave like a lead engineer instead of an autocomplete. The web search instruction gets it to actually check library docs instead of guessing at API signatures, which is where most of my early bugs came from. The deep think instruction pushes it into its reasoning mode. The do your best at the end is the part that I did not expect to matter, but it does. It triggers a longer, more thorough response every time.

Once the phase is green, I do not feed Claude Code the project. I feed it a short report. What was created, what was edited, what the tests said, and explicitly what I am uncertain about. Claude Code's job is not to redo the work. It is to catch architectural mistakes and propose surgical fixes, and in my experience it catches one to three real issues per phase, which are exactly the issues that would have been expensive to find later. The report format is deliberately structured, because if you do not list uncertainties, Claude Code will invent ones for you and you will spend tokens on stylistic preferences instead of real risk. Then qwen produces a.py for phase two, you run it, you report to Claude Code, and you repeat.

One rule I enforce with every qwen prompt is no code comments, anywhere, ever. Vibecoded projects do not benefit from comments. They benefit from the absence of comments. Comments drift, and if a comment says returns 200 on success and the function returns 201 now, an AI reading that comment makes wrong assumptions, and comments that drift are worse than no comments. They also cost tokens. A two thousand line file with fifteen percent comment coverage is three hundred lines of overhead you pay to upload and download on every round trip, and multiply that by forty files across six phases. And humans do not read them either. If you are working alone and using AI for everything, the code is not for humans. Name things well and the code documents itself. The only exception is machine readable pragmas like type ignore and noqa, which are not comments, they are directives.

The real numbers on a recent project, forty new files, twenty five modified files, six phases, were roughly eleven dollars across the whole thing and that was only because I was paying for Claude Code review. qwen cost me nothing. The naive Claude Code approach would have cost somewhere between one hundred eighty and two hundred fifty. The seventy percent figure is a conservative average because on projects where the plan is loose, qwen struggles more and Claude Code has to do more rescuing, and on projects where the plan is tight, the savings are higher. What I keep coming back to is that AI coding tools are priced as if reasoning and generation are the same thing, and they are not. Reasoning is expensive and worth paying for. Generation is cheap and mostly should not be paid at premium rates at all. Put each half of the job where it belongs and the bill collapses. The point is not the seventy percent. The point is that the meter stops being a design constraint. I can start a project on a Tuesday, finish it Thursday, and not wince at the counter. That is worth more than the savings.
